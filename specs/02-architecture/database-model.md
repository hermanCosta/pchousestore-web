### DATA-02 approved logical decisions

- Company owns Shops; `shop.code` is the stable sign-in identifier and is unique within its Company. `shop_access_credential` has one row per Shop, keyed by `shop_id`, and stores only the password hash and credential lifecycle metadata. Do not duplicate the Shop code in the credential row. The stable Shop identity (`shop.id`) is the OIDC subject; credential rotation does not change it.
- A Shop has zero or more historical `shop_session` rows. `shop_session.id` is the session identifier (`shop_session_id` / `sid`); persist no raw or hashed bearer/session token. A session has no employee identity. Idle/absolute expiry values and concurrent-device policy remain configurable/deferred; do not enforce a single active session per Shop.
- Protected commands validate employee code/password directly against the Company-wide employee credential at command start. The backend resolves the actor and checks active status, Company membership and feature-specific permission. No employee action-authorization token, table, entity, endpoint or authorization foreign key exists in the target model.
- Enforce tenant boundaries with composite candidate keys and FKs: a ShopSession belongs to its Shop; employee actors and Shop-scoped child records belong to the same Company/Shop as their owning operation. Where practical, carry the scope key in the FK instead of relying on application-only checks.
- Employee profiles are Company-wide and exactly one profile is active per Employee: `EMPLOYEE`, `MANAGER` or `ADMIN`. `ADMIN` inherits `MANAGER`; permissions are not calculated by unioning multiple active roles. The current persistence implementation uses `employee_role_assignment` as a profile-history table with a filtered unique index enforcing one active row per Employee.
- OpenIddict owns its persistence schema and migrations. Application tables may retain provider authorization identifiers for correlation/revocation, but do not depend on undocumented provider table structure.

## 1. Physical design standards

- DBMS: PostgreSQL 16 or later, using UTF-8 encoding.
- Primary keys: signed `BIGINT` paired with C# `long`; every FK uses the exact same SQL type as its referenced PK.
- Monetary values: C# `decimal` and PostgreSQL `NUMERIC(19,2)` for EUR transaction amounts. Rates/percentages use a separate higher-precision numeric type (for example `NUMERIC(9,6)`). The transaction currency is stored as ISO 4217 `CHAR(3)`; initial default is `EUR`.
- **Stock quantities:** no fractional product stock. `quantity_on_hand` and inventory movement deltas use signed integer types (`INT`/`BIGINT`) because negative quantity-tracked balances are allowed. Reservation, requested, ordered, received and returned quantities use non-negative integer types (`INT with a non-negative CHECK constraint`/`BIGINT with a non-negative CHECK constraint`) with positive-value and reconciliation constraints.
- Product quantities in SaleItem/ServiceOrderItem must be whole numbers. Service quantities may be treated separately if a future service-pricing requirement needs fractional units; service quantities never affect stock.
- Timestamps: PostgreSQL `TIMESTAMPTZ` stored in UTC; business-date calculations use Shop time zone. Initial Irish default: `Europe/Dublin`.
- Avoid `DOUBLE` for money.
- One Company is provisioned for the current deployment. Shared master data is company-level; operational records carry `shop_id`.
- Prefer `RESTRICT` for deleting financial/history records; use soft deactivation for master data referenced by history.
- No polymorphic source references for core transaction ownership. Use explicit nullable FKs where the source type is known.

### Financial reconciliation records

The two reconciliation tables above retain immutable execution history and detailed findings. A reconciliation run is read-only with respect to source financial ledgers. A PASSED run certifies only its recorded scope and check-set version; FAILED/INCOMPLETE findings remain available for investigation. The application must derive whether an aggregate is blocked from unresolved findings and any subsequent successful reconciliation, without editing or deleting the original run/finding rows. Finding resolution is recorded separately and must reference the finding and the authorized corrective action; never mark a finding resolved merely because a new run exists unless that run explicitly verifies the same aggregate/check and records the superseding evidence.

### Refund allocation relational integrity (DATA-05 implementation requirement)

- Expose candidate keys on `payment_transaction` and `payment_allocation` to support composite references. A refund header's (`original_transaction_id`, `kind`) must resolve to a valid original incoming transaction of matching type: `REFUND` -> `PAYMENT`; `DEPOSIT_REFUND` -> `DEPOSIT_RECEIPT`. The original must belong to the same target aggregate and currency as the refund.
- A refund allocation's composite reference must prove that `original_payment_allocation_id` belongs to the exact transaction referenced by the refund header and uses the same `payment_method_id` and currency. A refund allocation cannot point to an allocation from another original transaction, even if the tender matches.
- Enforce `original_payment_allocation_id IS NOT NULL` for every refund allocation and NULL for every non-refund allocation. Use database-enforced cross-row validation (constraint triggers or equivalent) for conditions ordinary CHECK constraints cannot inspect.
- Each refund allocation amount is positive. Sum of refund allocations equals the refund transaction amount; sum of original incoming allocations equals the original transaction amount. Allocation/source consistency is checked atomically.
- Calculate capacity independently per original allocation. CASH original received amount = `amount_tendered - change_amount`; CARD = approved/settled original allocation amount. Remaining capacity = original received amount less all linked PENDING and SETTLED refund allocations. A PENDING refund reserves capacity immediately, even though it has no drawer effect until SETTLED.
- FAILED and VOIDED refund transactions release their pending reservation. A REVERSED refund transaction does not release capacity and places the original allocation/transaction in a reconciliation-blocked state; no further refund is allowed until explicit reconciliation/correction. Do not automatically restore refundable capacity.
- The refund transaction's overall maximum is the sum of remaining capacities of the exact original allocations referenced. No tender substitution, cross-allocation offset or cross-tender reassignment.
- Refund header, allocations, idempotency record and required ServiceOrder Note are persisted atomically. Pending refunds do not affect the cash drawer; only a settled cash refund does.
- These are logical requirements, not production DDL. DATA-05 must verify PostgreSQL syntax, partial indexes, constraint-trigger semantics and EF Core mapping before migrations.

### Payment transaction and refund constraint-trigger matrix (DATA-05 review)

This matrix defines the first physical validation scope. It is a design specification only; it is not executable SQL and does not authorize migration generation.

| Trigger family | Table/event coverage | Deferred end-of-transaction validations |
|---|---|---|
| `payment_transaction_integrity` | Row-level constraint trigger on `payment_transaction` INSERT/UPDATE | Validate the final header state: positive transaction amount; exactly one valid target according to kind; refund kind/source-kind compatibility; original transaction exists, is a settled incoming transaction of the required kind, and matches the refund target aggregate and currency; no self-reference; a reversed original or an original with an unresolved REVERSED refund is blocked from further refunds. Validate that the transaction has at least one allocation and that allocation totals equal the transaction amount. |
| `payment_allocation_integrity` | Row-level constraint trigger on `payment_allocation` INSERT/UPDATE/DELETE | Validate the final allocation set for the affected transaction: every allocation amount is positive; tender-specific values are coherent; the transaction allocation sum equals its header amount; refund allocations reference the exact original allocation from the header's original transaction and preserve tender and currency; refund allocations require a non-null original-allocation reference and non-refund allocations require NULL. |
| `payment_refund_capacity_integrity` | Row-level constraint triggers on `payment_transaction` and `payment_allocation` INSERT/UPDATE; allocation DELETE is also covered so a source or refund allocation cannot be removed to bypass the check | For every affected original incoming allocation, recompute the received amount and linked refund reservations from persisted final rows. CASH received amount is `amount_tendered - change_amount`; CARD received amount is the approved/settled original allocation amount. Sum linked refund allocations only when their refund transaction is `PENDING` or `SETTLED`. Reject capacity below zero. FAILED/VOIDED refund transactions release capacity. Any linked `REVERSED` refund blocks further refunds until explicit reconciliation/correction; it does not release capacity automatically. |

**Trigger responsibilities and non-trigger constraints**

- Use ordinary `CHECK` constraints for row-local rules (positive amounts, valid cash/change ranges, required nullable-reference shape and target XOR where expressible), composite foreign keys for identity/scope/tender/currency relationships, and filtered unique indexes for unique source references. Triggers are reserved for cross-row and cross-table invariants; they do not replace simpler declarative constraints.
- A refund header must reference exactly one original transaction of the matching incoming kind: `REFUND -> PAYMENT`; `DEPOSIT_REFUND -> DEPOSIT_RECEIPT`. The original transaction must be `SETTLED`, and both transactions must target the same aggregate and currency. A refund may never target another refund.
- Every refund allocation references the exact original allocation named by the refund header, not merely any allocation with the same tender. Refund and original allocation tender/currency must match. The original incoming transaction's allocation sum and the refund transaction's allocation sum must each equal their respective transaction header amount.
- The capacity check is per original allocation, not just per original transaction. It must include all `PENDING` and `SETTLED` refund allocations, including a PENDING refund that has no drawer effect yet. It must not count FAILED/VOIDED refunds. A REVERSED refund is a hard reconciliation block, not spare capacity.
- A trigger caused by a refund transaction status change must validate the affected original transaction and all original allocations referenced by that refund. A trigger caused by an original transaction status change must validate its existing refunds; an original cannot become non-SETTLED or REVERSED while leaving new refund creation enabled.
- Validation must be symmetric: inserting/updating a refund header, inserting/updating/deleting a refund allocation, or changing a source transaction/allocation status or amount cannot bypass the same final-state invariants. Financial records must not be physically deleted through normal application paths; deletion events are covered defensively for allocation integrity, and production privileges/FKs must prevent deletion of settled financial history.
- Deferred trigger functions must identify the affected transaction/allocation from both NEW and OLD values as applicable, validate final persisted state, and tolerate multiple trigger invocations for the same aggregate in one transaction. They must not depend on trigger firing order or intermediate header/allocation statement order.

**Concurrency contract**

- The application acquires locks before writes using the previously approved canonical order: ServiceOrder first for ServiceOrder-linked operations; then original PaymentTransaction; then affected original PaymentAllocation rows ordered by ascending primary key. For non-ServiceOrder targets, lock the original PaymentTransaction before its affected allocations.
- After locks are held, reread source transaction status, original allocation received amounts, existing PENDING/SETTLED refunds and any REVERSED block. Validate and persist the refund header, allocations, idempotency record and required ServiceOrder Note in one transaction.
- The deferred trigger is a final database integrity backstop. It must not introduce a lock acquisition order that conflicts with the command contract. The implementation review must prove that concurrent refund attempts serialize on the original transaction/allocation locks and that the losing transaction cannot commit an over-refund.
- Under PostgreSQL `READ COMMITTED`, the implementation must verify trigger-query visibility after waiting on a lock and prove that the deferred validation sees committed competing reservations. If this cannot be demonstrated reliably with the chosen trigger function/locking pattern, DATA-05 must revise the physical strategy before migrations; do not rely on an unverified assumption about MVCC snapshots.

**Required PostgreSQL integration scenarios**

1. Valid single-allocation CASH and CARD refunds at the exact refundable cap.
2. Mixed CASH/CARD original payment with independent per-allocation caps; no cross-tender substitution or offset.
3. PENDING refund reserves capacity; a second concurrent refund cannot reserve the same amount.
4. FAILED and VOIDED refunds release capacity; SETTLED refunds consume it.
5. REVERSED refund blocks subsequent refunds until a separate reconciliation/correction path is completed.
6. Two concurrent refunds against one original allocation: one succeeds within the cap and the other receives a conflict or integrity failure; no over-refund commits.
7. Refund header inserted before allocations and allocations inserted before header validation; final valid transaction commits regardless of statement order.
8. Missing allocation, duplicate/wrong original allocation, wrong tender/currency, wrong original transaction, mismatched allocation sum, and mismatched target all fail at commit.
9. Changes to original transaction status/amount or original allocation amount cannot invalidate existing refunds silently.
10. Rollback removes the refund header, allocations, idempotency claim and ServiceOrder Note together; no partial financial effect remains.
11. Repeated deferred trigger invocation within one transaction remains deterministic and does not double-count an allocation.
12. Verify EF Core/Npgsql mapping and generated migration SQL against the supported PostgreSQL version; run concurrency tests using separate real database connections and transactions.

### PostgreSQL and EF Core physical-integrity implementation baseline (DATA-05 — approved technical review)

The Product Owner approved the following implementation strategy on 2026-11-22. This is a provider-specific design decision; it does not authorize production migrations or schema changes by itself.

- **EF Core / Npgsql model configuration:** map primary and alternate/candidate keys, composite foreign keys, conventional unique and filtered/partial indexes, column types/precision, nullability and row-local CHECK constraints. Use explicit composite keys wherever a child must prove that its referenced allocation, transaction, deposit, Shop or Company belongs to the same parent/scope. Configure PostgreSQL-specific filtered indexes with Npgsql-supported index filters.
- **PostgreSQL enforcement:** implement cross-row and cross-table invariants that cannot be expressed by ordinary CHECK/FK/UNIQUE constraints as PostgreSQL constraint triggers. In particular, refund header/type/target/currency consistency, refund-allocation source/tender/currency consistency, allocation sum equality, source transaction allocation totals, and per-original-allocation refundable capacity must be validated against the final transaction state.
- **Deferred validation:** use row-level `AFTER` constraint triggers declared `DEFERRABLE INITIALLY DEFERRED` where the invariant must observe the complete set of header/allocation/status changes made in one business transaction. Register validation triggers on both relevant parent and child tables so changing either side cannot bypass validation. Trigger functions must be deterministic, safe to execute more than once in a transaction, and validate the final persisted state rather than assuming a particular statement order.
- **Refund capacity and locking:** command handlers must acquire the already-approved canonical locks before writes: ServiceOrder first for ServiceOrder-linked operations, then the original PaymentTransaction, then its affected PaymentAllocation rows in ascending stable ID order. For non-ServiceOrder targets, lock the original PaymentTransaction before its affected allocation rows. Re-read authoritative amounts/statuses after locks. Capacity includes PENDING and SETTLED refund allocations; FAILED and VOIDED release capacity; REVERSED blocks further refunds pending explicit reconciliation/correction. Deferred triggers validate the same invariant at transaction end and must not introduce a conflicting lock order.
- **Migration ownership:** EF Core migrations own the trigger SQL and its teardown SQL. Trigger/function creation and removal must be explicit, repeatable in the migration lifecycle, and tested against the supported PostgreSQL version. No trigger is to be deployed through an untracked manual database script.
- **Verification gate:** before generating or applying any financial migration, DATA-05 must prove the composite candidate keys/FKs, filtered unique indexes, deferred constraint-trigger behavior, trigger interaction with concurrent transactions, rollback behavior, and EF Core/Npgsql model mapping using integration tests against real PostgreSQL. SQLite or EF InMemory tests are not substitutes for these provider-specific checks.
- **Scope boundary:** this decision approves the implementation approach only. It does not approve financial entities, production DDL, migrations, deployment or data conversion. Those remain gated by DATA-05 review and the migration backlog.

Reservation rules:

- `quantity_reserved` is a materialized counter maintained in the same transaction as reservation lines. It must equal the sum of active/unconsumed reservation quantities for that ShopInventory record.
- Reservation reduces availability, not on-hand. It creates no outbound `InventoryMovement`. For ServiceOrder requirements, stock receipt never allocates automatically; an employee explicitly selects the requirement and requested quantity. The reservation transaction checks and locks current availability, reserves no more than that amount, and supports partial reservation when available stock is below the requested quantity.
- Release decreases the reserved counter and records the reservation state/event; on-hand remains unchanged.
- Consume decreases both on-hand and reserved. At full settlement, consume active reservations exactly once for Sales and `FIXED` ServiceOrders; any unreserved quantity-based deduction follows the applicable settlement posting rule and may make on-hand negative. For `NOT_FIXED` ServiceOrders, consume only the actual used quantity explicitly recorded at handover, bounded by active reservations, and release the unused reservation. Serialized units must identify the exact physical unit and can never become negative.
- A released reservation does not guarantee stock later. Sale/`FIXED` settlement and `NOT_FIXED` handover may consume only active reservations and must never consume a released reservation or consume the same reservation twice. Quantity-based stock may become negative only under the applicable settlement posting rules; `NOT_FIXED` handover usage cannot exceed active reserved quantity. Serialized units require the exact available/reserved physical unit.
- `refurbished_unit` is reserved by its own status and is never represented as fractional or aggregate quantity.

Transfer ledger behavior:

- Dispatch validates source available stock, creates outbound InventoryMovement rows and sets status IN_TRANSIT in one transaction.
- Receipt records actual quantities, creates inbound movements at destination and updates status to PARTIALLY_RECEIVED or RECEIVED.
- Dispatched but not yet received quantity is in transit and is not counted in either Shop's available/on-hand stock.
- Accept only the counted, acceptable quantity, never more than dispatched. Short/damaged quantities stay outstanding and keep the transfer PARTIALLY_RECEIVED; overage is recorded but never added to stock under that transfer. An unresolvable loss stays open; no automatic write-off or transfer closure.
- Cancellation before dispatch has no stock effect. After dispatch use a reverse/corrective transfer, not a status-only cancellation.
- The dispatching and receiving employees must authenticate in their respective source/destination Shop sessions and belong to the same Company.

**Pickup idempotency and concurrency constraints**

- For Pickup, `operation_code = SERVICE_ORDER_PICKUP`, `resource_type = ServiceOrder`, and `resource_id` is the globally unique ServiceOrder ID. The unique key is scoped to the active Shop, operation and order.
- Store a cryptographic hash of the normalized request payload, excluding no business-significant fields. Never store employee passwords or other credentials in the request snapshot/hash input storage.
- Store the canonical HTTP response status and response JSON only after the command has produced its result, within the same database transaction as the Pickup state change, event, Note and stock disposition.
- Reusing a key with the same request hash returns the stored response. Reusing it with a different request hash or resource scope returns a conflict and never overwrites the original record.
- A failed transaction leaves no committed idempotency record, allowing a safe retry. A committed record is immutable.
- Serialize distinct Pickup commands by locking the ServiceOrder row and its active reservation lines (or an equivalent PostgreSQL-safe concurrency mechanism) before validating the current state and applying effects. The status transition must be conditional on the current eligible state; only one distinct command can transition the order to `PICKED`.
- The idempotency record is an operational command receipt, not a substitute for `ServiceOrderEvent`, `ServiceOrderHistory` or inventory ledger records.

**Canonical per-deposit liability formula (Product Owner decision, 2026-11-22):**
```text
available_held = settled_receipts - applied - settled_refunds - approved_forfeitures
```
Calculate independently for each ServiceDeposit. Receipts count only when the linked `DEPOSIT_RECEIPT` transaction is `SETTLED`; applications count only when the committed DepositApplication references that deposit; refunds count only when the linked `DEPOSIT_REFUND` transaction is `SETTLED`; forfeitures count only from valid `FORFEITED` events with mandatory reason and required Manager authorization. `RELEASED` has zero effect. **ServiceOrder refund/balance invariant (Product Owner decision, 2026-11-22):** a settled `REFUND` against a ServiceOrder payment does not reverse the original payment credit in `balance_due` and does not create a new customer debt. A `DEPOSIT_REFUND` reduces only the originating deposit's un-applied held liability; it does not change `balance_due`. Refunds are outgoing-funds records, not order-price or balance adjustments. Do not subtract refunds when reconciling `balance_due`. Any future change to the amount owed requires a separately approved, authorized and auditable balance-adjustment operation; no such table or behavior is approved by this decision. The balance cache is updated atomically with qualifying ServiceOrder payment credits and deposit applications under the ServiceOrder aggregate lock.

**Canonical ServiceOrder balance formula (Product Owner decision, 2026-11-22):**
```text
balance_due = service_order.total
            - SUM(SETTLED PAYMENT.amount_applied for that ServiceOrder)
            - SUM(committed DepositApplication.amount_applied for that ServiceOrder)
```
Only settled `PAYMENT` transactions targeting that ServiceOrder are counted; tender allocations are not summed separately. `DEPOSIT_RECEIPT` is excluded until explicitly applied. Refunds, deposit refunds and internal transfer-financial-event lines are excluded. Payment/application commands must reject amounts exceeding the current balance so the result cannot be negative. The formula is recalculated under the ServiceOrder aggregate lock; the materialized `balance_due` is updated in the same transaction as the qualifying ledger write. A mismatch between the stored value and the formula blocks new financial commands and requires explicit reconciliation; no automatic correction is allowed. All amounts must use the ServiceOrder currency.

### ServiceOrder aggregate concurrency and transaction strategy (technical review 2 — approved)

The approved baseline for ServiceOrder-linked financial, deposit, reservation and cross-Shop transfer commands is PostgreSQL `READ COMMITTED`, explicit row-level locks and transfer aggregate optimistic concurrency. Do not raise the database isolation level globally to `SERIALIZABLE` for these workflows.

- **Aggregate synchronization root:** every command that mutates or relies on mutable ServiceOrder financial/operational state must first lock its `service_order` row using `SELECT ... FOR UPDATE`. This includes payment settlement, deposit receipt/application/refund/forfeiture, payment refund, reservation reserve/release/consume when linked to an order, Pickup and transfer lifecycle commands. The order lock serializes the balance and order-level decision boundary; every participating command must follow this rule.
- **Canonical lock order:** (1) `service_order`; (2) `service_order_transfer` when the command concerns a transfer; (3) affected `service_deposit` rows ordered by ascending ID; (4) existing `payment_transaction` rows ordered by ascending ID when mutating/refunding them; (5) affected reservation rows ordered by ascending ID; (6) `shop_inventory` rows ordered by ascending ID. Acquire only the rows needed by the command, but never reverse this order. A transfer command may perform an unlocked read to discover its ServiceOrder ID, then must lock the ServiceOrder first, lock the transfer second, and revalidate all transfer/order state after both locks are held.
- **Authoritative reads:** after acquiring the ServiceOrder lock, reread balances, deposit ledger state, payment refundable remainder and active reservations. Values read before the lock or supplied by the client are advisory only. Deposit and payment mutations must lock the specific ledger owner rows before calculating available/refundable amounts. For multiple deposits/payments/reservations/inventory rows, lock in stable ascending primary-key order.
- **Transfer version:** every transfer state mutation checks the expected `version` and increments it conditionally (for example, `UPDATE ... WHERE id = @id AND version = @expectedVersion`). A zero-row update is a stale-version conflict; do not silently reload and apply the user's stale command.
- **Atomicity and idempotency:** persist the idempotency claim/result in the same transaction as all financial, stock, transfer, event and Note effects. An identical committed replay returns the stored result without repeating effects; changed-payload reuse is rejected. A failed transaction leaves no committed idempotency result or partial business effects.
- **Deadlocks/transient failures:** if PostgreSQL reports a deadlock or retryable transaction failure, retry the entire command transaction with fresh reads, fresh locks and the same idempotency key, using a bounded retry policy. Never retry only a suffix of the workflow. Domain/version conflicts are not transient and are returned to the caller.
- **Standalone stock commands:** commands not associated with a ServiceOrder may lock their ShopInventory/serialized-unit rows according to Stock rules. Any command touching a ServiceOrder reservation must acquire the ServiceOrder aggregate lock first, then follow the shared order above.

This strategy depends on all participating command paths observing the same aggregate-lock convention; a lock in the transfer handler alone is insufficient if payment, deposit or stock commands bypass it. Physical DDL, exact Npgsql/EF Core lock implementation and retry policy limits remain DATA-05 implementation-review items.

Each refurbished unit has a Company-unique internal asset code; capture a manufacturer serial when it exists and enforce Company-scoped uniqueness on normalized populated serial numbers.
18. `PaymentTransaction` target XOR: exactly one of Sale/ServiceOrder/ServiceDeposit; enforce kind-to-target combinations. Refund references original settled transaction and cannot exceed its remaining refundable amount under concurrency.
19. For a ServiceDeposit, settled receipts = applications + refunds + forfeitures + remaining held amount. DepositApplication is not a cash receipt and requires fresh employee code/password validation.
20. InstallmentPlan is restricted to serialized refurbished sales; schedule totals reconcile to the agreed total, and settlements cannot exceed individual or total outstanding balances. LAYAWAY handover occurs after full settlement; CREDIT_SALE handover requires explicit compliance gate. Every refurbished unit sale gets a 12-calendar-month commercial guarantee beginning at documented customer handover; statutory Irish consumer rights are additional and are not limited by this guarantee.
21. PaymentAllocation methods are data-configured per Shop. Only SETTLED transactions affect balance and close. Provider settlement fees/payouts are reconciled separately from customer tender.
22. Partial/total refunds are positive-magnitude transactions tied to original settled payment; cumulative refunds never exceed refundable balance. Physical stock return remains a separate selected StockReturn workflow.
23. Irish cash rounding is optional per Shop, only for an eligible cash-paid final bill total, to nearest €0.05. Record signed adjustment separately; do not round line prices, tax base or card/electronic payments. VAT calculation is controlled by CompanyTaxConfiguration.vat_enabled and effective-dated company tax codes/rates; tax setup must be reviewed before production tax-document finalization.
24. `DailyClosing` uniqueness remains `UNIQUE(shop_id,business_date)`; the approved operational formula is specified in `cash-closing-policy.md`. Accounting/tax mapping and processor settlement reconciliation remain subject to finance review.
25. `ServicePartRequirement` can reference only a product line belonging to the same ServiceOrder and Shop; requirement quantity is a positive whole number. The derived ServiceOrder portion of Parts to Buy reflects current uncovered quantity. Manual entries are stored separately in `manual_part_to_buy` and are Shop-scoped. Manual entries are physically deleted when removed; no removal history or restoration is supported. Deletion never changes ServiceOrder requirements or history.
28. `StoredImage` binary content and optional thumbnail use PostgreSQL `BYTEA`; application limits remain 10 MiB and 60 KiB respectively. Each owner-specific attachment table references `stored_image` using a foreign key. Image access is Shop-scoped and authorized. Validate file size, MIME by content, signature, dimensions and SHA-256. Do not use public URLs, object storage or filesystem paths. Deletion is soft/audited.
37. Totals and line prices are recomputed/validated server-side; never trust browser-submitted totals.

## 5. Stock lifecycle rules

| Scenario | Reservation | On-hand | Movement |
|---|---|---|---|
| Reserve quantity-based product | Reserved quantity increases | No change | No movement |
| Release/cancel reservation | Reserved quantity decreases | No change | No movement |
| Sale balance reaches zero | Active reserve consumed; remaining quantity deducted as needed | Decreases by sold product qty | `SALE_OUT` |
| ServiceOrder marked FIXED | Remains active | No change | No movement |
| Stock replenished through the Stock module | Increases available quantity only; no ServiceOrder reservation is created automatically. A separate explicit employee-authorized reservation action selects the target ServiceOrder requirement(s) and quantities. | Increases by stock-entry quantity | Stock-entry movement |
| ServiceOrder marked AWAITING_PARTS | Existing available portions remain reserved; no deduction | No change | No movement |
| FIXED ServiceOrder balance reaches zero | Active reservations consumed; remaining unreserved qty deducted as required | Decreases by used product qty | `SERVICE_ORDER_OUT` (pickup is a separate later event) |
| NOT_FIXED ServiceOrder balance reaches zero | No reservation or stock effect | No change | No movement |
| NOT_FIXED ServiceOrder handed over | Explicitly recorded used quantities consumed; all unused reserved quantities released | Decreases only by used quantity | `SERVICE_ORDER_OUT` for used quantity; release has no movement |
| Sale/ServiceOrder cancelled before stock consumption | Active reservations released atomically; consumed quantities are not reversed | No change from release; no automatic restock of consumed parts | No movement from release; physical returns use selected StockReturn/inspection workflow |
| Selected line physically returned (proposed) | No active reservation | No change while pending inspection | No movement |
| Returned line inspected and disposition is RESTOCK (proposed) | No active reservation | Increases by restocked qty | `RETURN_IN` |
| Transfer dispatched | Reserved qty cannot be dispatched | Source decreases | `TRANSFER_OUT` |
| Transfer received | Not applicable | Destination increases by actual received qty | `TRANSFER_IN` |

For serialized refurbished units, the equivalent operation is a status transition and a `-1` / `+1` movement tied to the exact unit, rather than changing a generic aggregate quantity.

## 6. Reporting and reconciliation semantics

- Gross sale/order value comes from Sale/ServiceOrder, not from summing tender allocations.
- Cash/card totals come from PaymentAllocation grouped by method, transaction kind and Shop.
- Operational reports default to current Shop context; Company-level reports may aggregate all Shops with explicit permission.
- Product stock report distinguishes on-hand, reserved, available and in-transit quantities.
- Transfer in-transit quantity is not included in either source or destination available stock.
- Serialized refurbished stock reports count `RefurbishedUnit` records by Shop and status; never add a second aggregate quantity that can drift.
- Return reports distinguish monetary refunds from physically returned quantities.
- Each Shop's expected drawer uses its own cash allocations and CashMovements only.

- Reservation-expiry automation is out of initial scope; reservations remain until explicitly consumed or released. Partial sourcing/reservation is supported for service-part requirements.
- Multiple warehouses/shelves/stock locations inside a Shop are out of initial scope; the initial model uses one stock pool per Shop.
- An explicit loss-adjustment/write-off process for unrecoverable transfer discrepancies remains out of scope; such transfers stay open until separately resolved.
- Refurbished unit identity is decided: company-unique internal asset code is required; manufacturer serial is captured when present and is Company-unique when populated. Acquisition/source details and commercial-guarantee coverage/exclusions are documented as proposed v1 policy in refurbished-condition-and-complaints.md, pending customer-facing legal review.

## ServiceOrder Pickup persistence requirements (2026-11-20)

The Pickup command must persist the following within one PostgreSQL transaction:
- Update `service_order.status` to `PICKED` and set non-null `picked_at`; retain the independent technical outcome (`FIXED` or `NOT_FIXED`).
- Insert one immutable `ServiceOrderEvent` with event type `SERVICE_ORDER_PICKED_UP`, server-resolved employee attribution, timestamp, and outcome-specific payload.
- Insert the append-only human-readable ServiceOrder Note in the same transaction.
- For `FIXED`, do not write stock movements or reservation changes. The normal full-settlement transaction remains responsible for consuming active reservations.
- For `NOT_FIXED`, persist each active reservation's used/released disposition; create `SERVICE_ORDER_OUT` movements only for used quantities, and release unused quantities without an inventory movement. Used quantity must be bounded by active reserved quantity. No unreserved line may be inserted by Pickup.
- Persist/claim an `idempotency_record` as defined in the Pickup idempotency and concurrency constraints. Scope it to Shop + `SERVICE_ORDER_PICKUP` + ServiceOrder + key; compare the normalized request hash; return the original committed status/body for an identical replay; reject changed-payload reuse; commit/rollback it with all business effects.
- Lock or concurrency-check the ServiceOrder and its active reservations so concurrent distinct Pickup commands cannot both commit. The losing command returns a conflict and the client refreshes.
- Do not model a direct undo/cancel transition. A future correction must be a separate auditable operation and must not automatically reactivate reservations.


### Deposit event constraint-trigger matrix (DATA-05 review)

This matrix defines the physical validation scope for the immutable ServiceDeposit event ledger and its source records. It is a design specification only; it is not executable SQL and does not authorize migration generation.

| Trigger family | Table/event coverage | Deferred end-of-transaction validations |
|---|---|---|
| `service_deposit_event_integrity` | Row-level constraint trigger on `service_deposit_event` INSERT/UPDATE/DELETE | Validate the final event shape and source linkage. `RECEIVED` must reference exactly one `DEPOSIT_RECEIPT` transaction in `SETTLED`; `APPLIED` exactly one committed `DepositApplication`; `REFUNDED` exactly one `DEPOSIT_REFUND` transaction in `SETTLED`; `FORFEITED` and `RELEASED` reference neither source. Enforce the required source-reference nullability, positive amounts for the first four event kinds, exactly zero for `RELEASED`, and mandatory reason for `FORFEITED`. Validate the event's deposit, ServiceOrder, currency and amount against its exact source. |
| `service_deposit_source_integrity` | Row-level constraint triggers on `payment_transaction` INSERT/UPDATE and `deposit_application` INSERT/UPDATE/DELETE (including status/commit-state changes) | Validate both directions: every settled deposit receipt/refund has exactly one matching event of the correct kind, and every `RECEIVED`/`REFUNDED` event points to the matching settled transaction; every committed application has exactly one `APPLIED` event, and every `APPLIED` event points to that committed application. Reject a source whose deposit, ServiceOrder, currency, amount, transaction kind, target or final status no longer matches its event. Non-settled receipt/refund transactions and uncommitted applications must not have effective events. |
| `service_deposit_liability_integrity` | Row-level constraint triggers on `service_deposit_event`, `payment_transaction` and `deposit_application` INSERT/UPDATE; DELETE coverage on event/application tables is defensive | Recompute each affected deposit independently from final persisted source rows. Posted liability is `settled_receipts - committed_applications - settled_refunds - approved_forfeitures`. `RELEASED` has zero effect. Reject a negative result, duplicate/missing source event, unsupported event shape, currency mismatch or inconsistent source amount. For a new `FORFEITED` event, validate that the forfeiture amount does not exceed the remaining held amount after prior committed applications, settled refunds, prior valid forfeitures and any outstanding pending-refund reservations. |
| `service_deposit_refund_reservation_integrity` | Reuse/coordinate with `payment_refund_capacity_integrity` on `payment_transaction` and `payment_allocation` INSERT/UPDATE and allocation DELETE | A `PENDING` `DEPOSIT_REFUND` reserves both (a) capacity on its exact original tender allocation under the payment refund matrix and (b) capacity against the deposit's currently available held liability. `SETTLED` consumes both capacities. `FAILED`/`VOIDED` release the pending reservation. `REVERSED` blocks further refunds and financial commands for the affected deposit until explicit reconciliation/correction; it must not automatically release capacity. The same refund must pass both independent caps. |

**Declarative constraints and source identity**

- Use row-local `CHECK` constraints for event-kind reference shape, positive/zero amount rules and mandatory local fields. Use composite candidate keys/FKs to prove that the referenced transaction/application belongs to the exact same `service_deposit` and `service_order`; do not rely only on application-side ID comparisons.
- Add unique source-reference constraints so one `payment_transaction_id` can back at most one deposit event and one `deposit_application_id` can back at most one deposit event. A transaction cannot be both a receipt and refund event, nor can an application be applied twice.
- Event amount must equal the exact source amount: `RECEIVED` and `REFUNDED` equal the linked PaymentTransaction amount; `APPLIED` equals the committed DepositApplication amount. All amounts and currencies must match the owning deposit and ServiceOrder. Amounts are positive magnitudes; event kind determines the financial direction.
- `FORFEITED` has no transaction/application source reference, requires a positive amount, mandatory non-empty reason and server-resolved employee actor. The required fresh `MANAGER` credential challenge is an application authorization precondition. A database trigger may validate actor identity/profile/status and persisted authorization evidence if such evidence is part of the approved schema, but it cannot claim to prove that a fresh password challenge occurred merely from an employee ID. Do not introduce an authorization token/table without a separate approved design.
- `RELEASED` has no source reference, amount exactly zero, and no liability or cash effect. It is an administrative release/unhold event only; it does not represent payment, refund, forfeiture, or a reduction of the deposit liability.
- Deposit events are append-only and immutable. Normal application/database roles must not update or delete them. Defensive triggers reject UPDATE/DELETE; privileged maintenance is outside ordinary application operation and must preserve the audit trail. Source records that contribute to a posted ledger cannot be physically deleted or silently rewritten.
- Deferred trigger functions must inspect both OLD and NEW affected aggregate IDs as applicable, validate the final transaction state, be deterministic and safe when invoked more than once, and not depend on trigger firing order. Register checks on both parent and child/source tables so changing either side cannot bypass the invariant.

**Liability and pending-refund capacity**

- The canonical posted liability remains:
  ```text
  available_held = settled_receipts - committed_applications - settled_refunds - approved_forfeitures
  ```
  Only `SETTLED` `DEPOSIT_RECEIPT` and `DEPOSIT_REFUND` transactions count; only committed `DepositApplication` rows count; only valid `FORFEITED` events count. `RELEASED` contributes zero. Pending/failed/voided transactions are excluded from this posted-liability formula.
- Separately, command-time spendable capacity is `available_held - pending_deposit_refund_reservations`. This reservation does not rewrite the posted liability formula: it prevents multiple pending refunds from reserving the same held funds. Each pending refund is counted once by its transaction/allocation source, not again through its event (a `REFUNDED` event is created only when the refund is settled).
- A `DEPOSIT_REFUND` must pass both the exact-original-tender refundable cap from the PaymentAllocation refund matrix and the deposit-level spendable held-capacity check. Passing one cap does not waive the other. No tender substitution, cross-deposit pooling, offsetting or reallocation is allowed.
- `FORFEITED` is validated against the held amount remaining at its posting boundary, net of committed applications, settled refunds, prior valid forfeitures and pending deposit-refund reservations. A forfeiture cannot consume funds already applied, refunded or reserved by a pending refund. The event, reason, actor attribution, idempotency record and any required ServiceOrder Note are persisted atomically.
- A materialized held balance is only a cache. Recompute authoritative values after locks; any missing, duplicate, unsupported, mismatched or negative ledger state blocks the affected deposit's financial commands and related transfer acceptance until explicit reconciliation. Reconciliation remains read-only and never auto-corrects.

**Locking, transaction boundaries and authorization**

- Every deposit mutation first locks the owning `service_order` row using `SELECT ... FOR UPDATE`, then the affected `service_deposit` row. For commands affecting multiple deposits, lock deposits in ascending stable ID order.
- For a `DEPOSIT_REFUND`, continue the canonical lock order after the deposit lock: lock the original `payment_transaction`, then its affected original `payment_allocation` rows in ascending ID order. Re-read source status, original tender capacity, deposit liability and pending reservations after all locks are held. Do not reverse the approved global order: ServiceOrder -> ServiceDeposit -> PaymentTransaction -> PaymentAllocation.
- Receipt settlement, application, refund, forfeiture and their event/source records, required ServiceOrder Note, idempotency record and materialized cache update must commit or roll back atomically. No deposit event is a cash movement by itself; only the linked settled receipt/refund transaction has the corresponding tender/drawer effect.
- Application authorization remains feature-specific: deposit receipt/application/refund commands require their already-defined employee credential/role checks; forfeiture requires a fresh `MANAGER` credential challenge. The trigger validates persisted relational and amount invariants, not the authenticity of a credential challenge unless an explicitly approved evidence mechanism is added.
- Use conditional version updates and shared idempotency semantics. An identical replay returns the original committed result; changed-payload reuse is rejected. A concurrent command that loses the aggregate lock/version race must fail as a conflict or retry the whole transaction within the existing bounded transient-retry policy.

**Required PostgreSQL integration scenarios**

1. Each of the five event kinds accepts only its exact source-reference shape; malformed, missing or extra references fail at commit.
2. `RECEIVED` requires a settled `DEPOSIT_RECEIPT`; pending/failed/voided/reversed or wrong-kind transactions cannot back it.
3. `APPLIED` requires one committed application belonging to the same deposit and ServiceOrder; uncommitted, duplicate, wrong-deposit or wrong-amount application fails.
4. `REFUNDED` requires a settled `DEPOSIT_REFUND` linked to a settled receipt for the same deposit; pending/failed/voided/reversed or wrong-target/currency sources fail.
5. Every valid settled receipt/refund and committed application has exactly one matching event; changing source status/amount/target or deleting a source cannot silently orphan or invalidate the event.
6. Duplicate transaction/application source references, event amount mismatch, currency mismatch and composite-FK scope mismatch fail.
7. `FORFEITED` requires positive amount, non-empty reason, actor and MANAGER authorization at command boundary; amount above held capacity or reserved pending-refund capacity fails.
8. `RELEASED` accepts only zero amount and no financial references; it never changes liability or cash/drawer totals.
9. Multiple deposits on one ServiceOrder are reconciled independently; no cross-deposit pooling or offset is possible.
10. A `DEPOSIT_REFUND` that is within the original tender cap but exceeds deposit held capacity fails; one within held capacity but above original tender capacity also fails.
11. PENDING deposit refunds reserve held capacity; FAILED/VOIDED release it; SETTLED consumes it; REVERSED blocks further commands pending explicit reconciliation.
12. Concurrent application/refund/forfeiture attempts against one deposit cannot over-consume held liability; concurrent refunds also cannot exceed any original tender allocation.
13. Rollback leaves no partial event, transaction, application, Note, idempotency record or cache update.
14. Repeated trigger invocation is deterministic and does not double-count source records or events.
15. Run tests using separate connections against the supported real PostgreSQL version and EF Core/Npgsql mappings; SQLite is not an acceptable substitute for deferred-trigger/concurrency verification.
16. Specifically prove that deferred trigger queries under PostgreSQL `READ COMMITTED` observe competing committed reservations after lock waits. If they do not, revise the physical validation strategy before creating migrations; do not assume the trigger matrix alone proves this behavior.



### Derived ServiceDeposit status and independent review flag (DATA-05 lifecycle review)

The five deposit statuses are derived projections, not a command-driven state machine. The event/source ledger remains authoritative; status must be recomputed from committed financial facts and must never be used as a second source of monetary truth.

Let:

- `settled_receipts` = sum of valid settled `DEPOSIT_RECEIPT` transactions for this deposit.
- `dispositions` = committed applications + settled deposit refunds + valid authorized forfeitures.
- `available_held` = `settled_receipts - dispositions`, using the canonical liability formula above.

Derive the status in this precedence order:

1. `OPEN`: no settled receipt exists.
2. `CLOSED`: settled receipts exist and `available_held = 0`; the deposit has no remaining held liability because all received funds have been applied, refunded or forfeited.
3. `PARTIALLY_DISPOSED`: `available_held > 0` and at least one positive application, settled refund or valid forfeiture exists.
4. `PARTIALLY_FUNDED`: no disposition exists and `0 < settled_receipts < target_amount`.
5. `HELD`: no disposition exists and `settled_receipts >= target_amount`.

The derived status is a projection/cache and may be recalculated when a valid new source transaction is committed; it does not itself authorize or perform a financial operation. A pending refund reservation does not change the posted liability formula or derived status, although it reduces command-time spendable capacity. `RELEASED` events do not affect the derived status. Do not introduce `APPLIED`, `REFUNDED` or `FORFEITED` as mutually exclusive deposit statuses: those are ledger facts and can coexist over the life of one deposit.

The `review_required` operational flag is independent of status. It may be raised by the existing 90-day no-customer-response review rule, can coexist with any derived status, and has no effect on liability, refundability, application capacity or Shop transfer. Clearing the flag is an operational acknowledgement, not a financial event. No automatic expiry or forfeiture follows from this flag.
